# PRG-7. Типы и описание программы

**Автор:** Денис Юрченко, тимлид · **Неделя:** 7

Коллеги, пилот идёт, и у нас первое замечание от Ирины Павловны: к запуску на всех группах колледж хочет документацию «как положено» — учебная часть сдаёт отчёт о внедрённых системах, и ей нужен документ по ЕСПД [Б8]. Заодно — вещь для нас самих: код вырос до восьми модулей, и «что сюда передают и что отсюда возвращается» уже не держится в голове. Пусть это знает mypy.

## Что сделать

### 1. `mypy --strict` на весь пакет

- Добавьте mypy в зависимости разработки: `uv add --dev mypy` — и закоммитьте изменённые `pyproject.toml` и `uv.lock`.
- Аннотируйте **всё**, чтобы `uv run mypy --strict progon` не находил ни одной ошибки. Подсказки:
  - типы из `collections.abc` в параметрах (`Iterable`, `Mapping`, `Sequence`) и конкретные — в результатах (`list`, `dict`);
  - повторяющиеся типы — псевдонимами: `type Key = tuple[str, str]`;
  - результат разбора JSON — `Any` честно, а то, что вы из него собрали, — точно: `TypedDict`;
  - альтернативный конструктор возвращает `typing.Self`;
  - `Attempt.__iter__` распаковывается в разнотипные значения, и mypy этого не выразит — дайте попытке метод, который возвращает кортеж с точными типами, и передавайте в `gradebook` его;
  - если mypy ругается на циклический импорт `model` ↔ `course` — импорт внутри функции с комментарием, почему.
- Файл `progon/py.typed` (пустой) — маркер PEP 561: «в пакете есть аннотации, проверяйте по ним». Без него mypy в чужом проекте, который использует «Прогон», будет считать все наши функции нетипизированными.

Поведение не меняется: все старые проверки остаются зелёными.

### 2. Docstring

У каждого публичного модуля, класса, функции и метода — docstring: что делает, а не как. Проверка — `ruff check --select D1 --ignore D105,D107 progon` (магические методы и `__init__` — можно без).

### 3. Описание программы — `docs/DESCRIPTION.md`

По ГОСТ 19.402-78 «Описание программы», разделы в порядке стандарта:

1. **Общие сведения** — обозначение, наименование, необходимое ПО, язык.
2. **Функциональное назначение** — какие задачи решает и с какими ограничениями.
3. **Описание логической структуры** — модули пакета (все, таблицей) и их связи; **схема алгоритма** одной команды по ГОСТ 19.701-90 — нарисуйте её в Markdown как `mermaid`-блок `flowchart` (GitHub покажет картинкой): терминаторы, данные, процессы, решения.
4. **Используемые технические средства**.
5. **Вызов и загрузка** — установка и команды.
6. **Входные данные** — форматы: файл курса JSON, отчёт JUnit XML.
7. **Выходные данные** — ведомость (в том числе CSV), сводки, сообщения об ошибках.

Руководство пользователя (PRG-6) — для преподавателя: как работать. Описание программы — для того, кто будет её сопровождать: как она устроена.

- `make check-typ7` и `make check-doc7` зелёные, старые — тоже.
- PR `prg-7` в `main`. В описании: три ошибки или неточности, которые mypy нашёл в вашем коде, и как вы их исправили.
